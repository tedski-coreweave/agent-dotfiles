# CI failure triage

Input: a link or reference to a failure. Output: a verdict with
evidence and an action. The question is always the same: is this a code
problem, a flaky test, or flaky infra?

## Environment (this machine)

- `pup` (Datadog CLI) needs `DD_TOKEN_STORAGE=file` because flox/nix
  envs break macOS keychain. Prefer pup over Datadog MCP or raw API.
- Run Slack-MCP reads outside the ~/src/core flox env.
- Never hand-convert dates or infer timestamps. Pull them from the
  tools and pin the exact window in every query you run.

## Process

1. Resolve the link to a concrete run.
   - GHA: `gh run view <id> --log-failed` (repo-scoped; get the repo
     from the URL, don't assume core).
   - CircleCI: `circleci` CLI; config is generated by
     `.circleci/generate_config.py` in core, so config errors may be
     generator bugs, not YAML edits.
   - Slack thread: read the thread, extract the actual run link, then
     start from that. The thread's diagnosis is a hypothesis, not
     evidence.
2. Isolate the first real failure. Ignore cascade noise (jobs that died
   because a dependency died).
3. Get history before diagnosing. One red run proves nothing.
   - Same test/job on master and other branches: repeated failure on
     unrelated branches points at flake or infra, not this diff.
   - Playwright/integration: check Currents for shard-level pass rates
     and retry patterns.
   - Datadog: merge-health dashboards and CI monitors via pup.
4. Classify:
   - Code bug: failure is deterministic, tied to the diff, reproduces.
     Evidence: first failing commit, failing assertion that matches
     changed behavior.
   - Flaky test: intermittent, fails across unrelated branches, retries
     pass, timing/ordering sensitive. Evidence: pass/fail history, retry
     outcomes.
   - Flaky infra: runner death, network/registry timeouts, resource
     exhaustion, queue weirdness. Evidence: infra-level error lines,
     correlated failures across unrelated jobs at the same time.
5. Act by class:
   - Code bug: point at the diff and the owner (use CODEOWNERS
     resolution, not grep). Fix if it's ours and small.
   - Flaky test: quantify the flake rate, then quarantine/fix/route to
     the owning team with the evidence attached.
   - Flaky infra: check for a matching known issue first; escalate with
     the correlation evidence, note it for the friction log (frog) when
     working in core.

## Output format

```
Verdict: code bug | flaky test | flaky infra (confidence)
Evidence: links, run IDs, pass/fail history, exact timestamps
Blast radius: who/what else is hitting this
Action: fix (diff attached) | quarantine + route to <owner> | escalate
Unverified: anything asserted without tool evidence
```

Keep it copy/pasteable for Slack or a ticket. State confidence
honestly; a wrong confident verdict costs more than an honest "60/40
flake, here's the discriminating experiment".
