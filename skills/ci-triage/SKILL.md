# CI failure triage

Input: a link or reference to a failure. Output: a structured report
where each field is independently supported by evidence.

Do not collapse the report into a single label. "Flaky test" bundles a
failure surface, a cause, and a repeatability claim into one word, and
the bundle is usually wrong in at least one dimension. Report the
dimensions separately and let the disposition follow from them.

## Operating rules

- Evidence before labels. Every field cites a run, query, or log line.
- Unknown is a valid answer. An honest unknown with the next
  discriminating step beats a confident guess.
- Collapse cascades. Report the first causal failure, not every job
  that died downstream of it.
- Count causes, not red jobs. Twenty red jobs from one runner outage is
  one cause.
- Preserve test intent. A test that catches a real defect keeps
  catching it.
- No masking. Do not add arbitrary retries, sleeps, raised timeouts,
  weakened assertions, or skips to make a signal go away.
- A fix proposal needs a red loop first: a runnable check that shows
  the failure now and goes green when fixed. No red loop, no fix claim.
- Quarantine is containment, not a classification outcome. It requires
  a denominator, a time window, and explicit human approval. Never quarantine as
  the automatic consequence of calling something flaky.

## Environment (this machine)

- `pup` (Datadog CLI) needs `DD_TOKEN_STORAGE=file` because flox/nix
  envs break macOS keychain. Prefer pup over Datadog MCP or raw API.
- Run Slack-MCP reads outside the ~/src/core flox env.
- Never hand-convert dates or infer timestamps. Pull them from the
  tools and pin the exact window in every query you run.

## Process

1. Resolve the reference to a concrete run.
   - GHA: `gh run view <id> --log-failed` (repo-scoped; get the repo
     from the URL, don't assume core).
   - CircleCI: `circleci` CLI; config is generated by
     `.circleci/generate_config.py` in core, so config errors may be
     generator bugs rather than YAML edits.
   - Slack thread: read it, extract the run link, start from the run.
     The thread's diagnosis is a hypothesis, not evidence.
2. Find the first causal failure. Walk back from the reported symptom
   to the earliest step that failed on its own.
3. Normalize the signature. Reduce the failure to a stable string
   (assertion, error class, exit path) so it can be counted and matched
   against history.
4. Gather the denominator before making any repeatability claim. One
   red run supports no claim at all.
   - Same job/test on master and unrelated branches over a pinned
     window.
   - Playwright/integration: Currents shard pass rates and retries.
   - Datadog via pup: merge-health dashboards, CI monitors.
5. Resolve ownership with the codeowners tool, not grep.
6. Fill the report. Leave a field unknown rather than inferring it.

## Report

```
Surface:        <pipeline/job/step/test, and the first causal failure>
Signature:      <normalized error or assertion>
Cause:          <mechanism, or unknown>
Repeatability:  deterministic | known flake | likely transient | unknown
                <denominator: N failures / M runs, window, source>
Ownership:      <team or owner, from codeowners>
Confidence:     high | medium | low, and what would raise it
Disposition:    <fix | route | escalate | contain | needs more evidence>
Next action:    <the specific authorized step>
Unverified:     <anything asserted without tool evidence>
```

Keep it copy/pasteable into Slack or a ticket.

## Disposition guidance

- Deterministic and ours: fix it, smallest change that addresses the
  cause.
- Deterministic and not ours: route to the owner with the signature and
  the first causal failure.
- Known flake: work to raise the reproduction rate (tighter loop,
  repeated or stress runs, narrowed scope) rather than demanding one
  clean repro before acting. Report the rate with its denominator and
  window, then propose a real fix. Containment (quarantine) needs explicit human approval and
  is temporary, with the follow-up recorded.
- Likely transient infra: look for a matching known issue first, then
  escalate with the correlation evidence. Log friction with `frog` when
  working in core.
- Unknown: state the discriminating experiment that would resolve it.
